# WriterForge 0.T｜《凡人》逐段可见 vs 不可见，第一轮真实作品与句子问题（2026-10-25）

**唯一真实来源：** [Actions #40163959949](https://github.com/66tyu55/WriterForge/actions/runs/40163959949) 的原始供应商回包与 `WF-0T-Real-Fanren-Staged-A-vs-B-Initial-Pair-20261025`。实验代码：`experiments/wf_fanren_staged_source_ab_0t.py`。仍是开发分支 `refactor-unified-scene-delivery-audit`，没有修改 main、R2 原小说、Railway 或正式 Canon。

## 一、第一阶段实际发生什么

- 真实旧有私有 R2 版本《凡人修仙传》通过完整 SHA-256 和原有单书存储验证。原始编码为 GB18030，原文 **15,079,878 字节**；第一次误用 UTF-8 导致阻断后，已统一复用旧 `modern_source._encoding/_chapters`。逐步阅读只取第 1、2 章开头各 **230 字符**，原著内容不进入 GitHub artifact，A 的模型请求没有原著。
- **6 次真实 DeepSeek Flash 调用**：A T1、A 作者判断、A T2、B T1、B 作者判断、B T2。共 `prompt_tokens=7,141`、`completion_tokens=1,774`，每次保留真实 provider wire SHA。没有重用旧模型输出冒充新文学创作。
- 原创《潮簿》冻结同一人物/共同大纲/两个事件段目标，两边都是原 WriterForge 的 `V96 → V114 → V117`，分别先写 T1 再生成 T2，禁止一次性生成整章。B 在 T1 和 T2 分别仅额外读取当前窗口；它未收到全书或完整第一章。
- 两个真正作者在 **T1 后均选择 `MOVE_ON`**，没有发生 `LOOK_BACK_NOW`；这是作者真实回复而非软件自评。没有启动 V119。A、B 都建立了**未接受**的 2 段合并稿和单一 NarrativeCore 候选签名。**程序/结构通过不是文学质量通过。**

## 三、真正被原有程序漏检的来源问题

**B 的 T1 源：** “他照做了，打结时潮水正退，露出桩底一圈新裂的细纹。”（前文明确程满要求“系在木桩上”）。B 的 T2 开头，出现三处具有同一段来源 SHA 的精确锚点：

- 索引 offset 12：`手里攥着那截麻绳`。
- offset 21：`绳结还系在木桩上`。
- offset 32：`绳子被人从桩头解下来`。
- offset 266：`重新系回木桩`。

“绳结仍系在木桩”与“绳子已从桩头解下”出现在同一次当前状态的叙述中；若指同一条绳、同一个绳结，则需要真实文本解释，不能同时冒充已确定状态。**目前属于带两处唯一字面原句的物件连续性高可信疑问**，不是程序已经证明“作者审美错误”。在这份正文上，`V96` 行为/后果引用、`V114` 候选状态、`V117` 续写预检仍全部通过。可见通用普通物件的空间/绑缚关系并未得到完备覆盖。

**A 的 T2 另有轻度未证前史：** “先照程满教的法子”，此前 T1 正文没有写过程满教授贴耳听堤的方法。可能是可接受的跳时/留白，但不能把这件尚未明写的行为直接晋级为上一段确证知识。A 的另一方面有真实可见的“修堤派工、签名担责”后果，不能和上述未证来源一概划成同分。

## 四、关键架构发现：T2 根本没被问过是否要自主回头

这次隔离 A/B 代码只在 T1 之后调用 `_ai_decides_when_to_revisit`，T2 写完后没有再让同作者复读和决定。**所以 T1 的两次 `MOVE_ON` 根本不能证明作者看过 T2 的物件矛盾。** 若说“AI 反复检查过仍找不到”，就是不真实的反例统计。

## 五、按 0.T 真闭环继续，而非硬喂错误答案

新脚本 `experiments/wf_0t_real_B_reader_repair_downstream_20261025.py` 只读重放 #40163959949 的真实 B T1/T2 及全部源 SHA；不再下载/读取原著，也不重新调用原来的 6 次 API。之后：

1. **独立同作者读者视角**只看它亲写的 T1、T2，用原 `_reader_separates_written_and_inferred` 给出书面来源原句及有边界的未证过渡，不向模型指定“绳结必错”。来源凭证只能认证字面引句，不把模型推测当事实。
2. **同一个 DeepSeek 回原作者**自行选择 `MOVE_ON` 或 `LOOK_BACK_NOW`、改哪段、为何。不能靠外部代码强迫回改。若 `MOVE_ON`，如实报告“未进入改稿”，保留疑问。
3. **若主动改写**，WF 先给现有源锁修复契约，同一作者完成最多两轮 V119（其中只有原已允许的 1 次来源 trace-only 补交），仍过 V96/116/114/117、前后状态风险、循环保护。
4. **若改 T1**：撤销依赖旧 T1 的 T2 候选，由同一作者重写 T2。**若改 T2**：原作者自己先构思单一新 T3，再写一个小段。不可拿旧废稿下游冒充新创作。
5. 保存变动前后原文、未证风险、所有真实 model wire、真实新段与本地签名的统一图快照。不写新文学记忆，不新增审稿模型，不接受 Canon，仍待匿名人类读者评价；若任一步失败，保存拒稿并结束，零自动重试。

**额度边界：** 最多 **6 次新增同一写作模型请求**，8,000 output-token 预留；先完成零付费真实旧原文 SHA 核验与工程回归，通不过绝不扣模型费用。

**不可宣称已成功的内容：** B 的原问题是否被作者发现、是否修好、是否引入新位置错误、真实新下游是否写成、文笔是否改善，均需下次实测与读者查看原稿。任何旧的绿灯/模拟结果都不能替代。
