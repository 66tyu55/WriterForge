# V26：WriterForge 自动伴随写作（无需用户手动检索）

## 写作时：作者只负责写，技能在内部完成

- 通过我们提供的真实本地浏览器编辑器捕获 input 事件；普通 Python Skill 无法监听任意软件里的按键；
- 停笔约 900 毫秒再向本地写作执行器请求建议，避免每打一个字就调用模型；
- 意图路由寻找明确情境，例如性格倔强的女子、妖兽露出獠牙、天劫，而不是因一个山或雷字断定环境或雷劫；
- 自动调用已有 CraftEngine、已发布 Xuehai 快照，以及 V25 人工核对过的百科证据，永不把 proposed 误当 verified；
- 本地模型返回两段不同的原创续写，作者单击采用才插入到光标处；忽略不打断原稿；
- 自动写本地草稿文件，刷新网页恢复；仅将作者采用选项记为弱信号，不自动变成永久风格规则；
- 如果模型没有响应或返回不合格式，不会以人工写死模板伪装成功；
- 900 毫秒只指停笔触发时间，不包括真实模型的推理时间。没有模型就没有可用的自动提案。

## 自主写作：大纲 → 章节计划 → 文学技能 → 正文

- 输入原创故事大纲和每章的具体目标（每次最多六章）；
- 每章先真正让本地模型制定人物目标、冲突、决定、结果、叙述视角；
- 使用当前学海快照检索相关结构，调度最多两组写作技法，从 verified 百科中取有限依据，再生成原创正文；
- 每章保留 candidate.md、run.json 和 chapter_plan.json，来源证据、模型、提示词哈希均可验证；
- 下一章只参考上一章最多 750 字临时尾部，不会无限积累上下文；
- 草稿不会自动变成作者已接受正文，也不会在没有作者确认时提升 WriterForge 文学技巧权重。

## Windows 实际使用

需要先在本机恢复某一个学海 SQLite 文件，且内部有真实已发布原著快照。
目前《西游记》《红楼梦》《水浒传》仍是独立存储的学海，不宣称自动合并三库。

启动 LM Studio 或 OpenAI Chat Completions 兼容的本地模型服务，确保实际模型已加载。
在 WriterForge 项目目录中：

    python -m pip install -e .
    writerforge --db corpus/library/已恢复学海.sqlite3 studio --project my-novel --scene chapter-01.scene-01 --goal "两个旧友因承诺陷入冲突" --model "你的本地模型ID"

浏览器打开：

    http://127.0.0.1:8765/

正常输入汉字即可，内部触发分类与技法路由，侧边栏给出两种选择。
Ctrl+1、Ctrl+2 可以直接采用第 1 或第 2 种建议。
切到“你写 · 自动规划”可以提交大纲和章节目标，让本地模型实际生成并保存候选章节。

普通的 ChatGPT 输入框、Word、Google Docs、Unity 或其他编辑器并不会因此被监听。
要在那里做到同样体验，需要有用户授权的编辑器插件或原生集成；当前 V26 只保证自带本地写作编辑器。

## 存储、安全、成本

- 服务仅在本机 127.0.0.1 上监听；请求需要本地令牌与同源校验；
- 正文文本、生成候选、作者选项均留在本地 writing_runs/studio；
- 不会自动把未发表作品上传公开 GitHub Releases，也不会自动同步到 Cloudflare R2；
- 请求最多约 30KiB，正文编辑区最多 12000 字符，选项只生成两段，单次自主作业最多 6 章；
- 同时最多一个本地模型作业；作者选择历史最多保留 128 条；
- 不允许直接调用公网模型接口；作者对本地模型的安装和启动有控制权；
- 当前三部原著的八轨索引仍属于未验证结构线索；只有 verified 百科素材能作为正式实体属性输入；
- 不复制整本原著到提示词，不让现代有版权小说自动进入公开云存储。

## 验收范围与未完成

工程测试可以核对事件触发、自动保存、内存和并发限制、两种备选、逐章实际模型调用、来源追溯和候选生成保存。
不能由这些测试推断所有生成语句都有文学质量，也没有做真人盲评。
你要求的至少 50 部作品之后才开展的整体文学成果评估和技能统一优化仍然没有启动。
