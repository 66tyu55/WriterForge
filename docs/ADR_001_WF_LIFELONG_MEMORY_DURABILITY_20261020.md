# ADR-001 · WriterForge 终身学习与长期记忆完整性契约

- **状态**：ACCEPTED AS ARCHITECTURAL REQUIREMENT（架构约束已确认；生产端到端实现尚未验收）
- **决定日期**：2026-10-20
- **范围**：所有未来的 LEARN、Xuehai、FactJournal、ExperienceDecision、R2、SQLite、WRITE、迁移和发布流程
- **来源**：用户明确要求「WF必须是长期发展，不能短时存储一点手法知识，后面再使用突然变成乱码/笨蛋」。
- **优先级**：P0，先于增加训练章数、扩写提示词、晋级文学等级、上线新写作功能。

## 0. 不可退让的目标

**长期发展不等于存几条“写作手法笔记”。** WF 必须能在重启、断网、换设备、跨会话、代码升级、模型供应商切换和多年积累后，恢复**来源可信的结构化经验**，辨认其适用条件、反例与时间/人物关系，并证明这些经验仍影响真实决策、没有劣化或被污染。

若只证明 R2 有对象、SHA 相同、提示词里出现“上一章策略”，应标记 `STORED_NOT_LEARNED`，绝不能宣称“WF已经成长”。通过 API 调用 DeepSeek **不会自动更新模型权重**；WF 的长期学习必须是自身可迁移、可验证、可检索、可撤销的外部经验与行为系统，而不是寄望模型会凭空记住。

## 1. 三项必须分别验收的能力

1. **字节持续存在（DURABLE）**：原著和候选/经验/失败不可变记录跨进程恢复，校验原始字节、字符编码、格式版本、源SHA、事件链及manifest；本地临时目录/提示上下文/单次Railway容器永远不能被视为长期源。
2. **语义关系仍可恢复（RECONSTRUCTIBLE）**：找回人物身份、每个人在当时已知/未知的事实、角色与读者知识边界、故事时序、触发场景、因果假说、替代解释、反例、审核状态、来源位置、上一版本和撤销墓碑。文本出现乱码、断章或字段语义变化时应立刻失败隔离。
3. **行为仍能改善（BEHAVIORALLY VERIFIED）**：恢复后的经验需通过可追溯的 SELECT/SKIP/ABSTAIN、重启后一致的策略选择及独立作品盲考检验。即使字节恢复成功，也不能直接推出文学理解或创作质量提升。

任何一层未过，状态必须为 `UNVERIFIED`、`QUARANTINED` 或 `RESTORE_BLOCKED`，不得用另一层的“绿灯”覆盖失败。

## 2. 单一可信数据流；不新造第二套无关联记忆库

```text
私有R2原著/已验证原始来源
    → PASS A逐单位首读（不可改事件、前后SHA链、seal）
    → PASS B来源绑定的观察/机制候选（V89宿主精确定位）
    → FactJournal已有跨章身份/人物知识/记录与故事双时钟快照
    → 可反证的文学候选 + 错误/反例/审查结果
    → ExperienceDecision现有独立审核、版本/撤销、受限实验授权
    → WRITE只按当前可信版本选择抽象策略 + 写后回执
    → 下一次LEARN以真实失败/盲评证据修订，保留旧记录
```

- 复用 `writerforge/r2_learn_journal.py`、`v79_provisional_r2_cas_journal.py`、`r2_storage.py`、`study_storage.py`、`fact_journal.py`、`experience_decision.py`、`db.py`。**不因为方便而复制原著或人物关系到新的平行数据库。**
- `writerforge/memory.py` 当前的 `MemoryBudget.select` 只是上下文筛选器，**不是持久学习存储**；L0/L1/L2/L3/L4/ARCHIVE 标签不能代替 R2/SQLite 备份、恢复和语义回放。
- 原文库、经验库、运行索引/缓存严格分开。索引丢失应可从可信快照再建，丢索引不得视为永久遗忘；普通检索不要求每次下载全文，WRITE不得靠复制原著短句“模拟经验”。
- R2实验CAS与本地SQLite不是一个已证明原子提交的持久系统：正式接线前要有 manifest-last、失败恢复和双账本补偿协议；**不得假称V85–V89已有端到端生产级永久记忆。**

## 3. 所有可长期使用的经验必须有版本化身份

每条经验的持久契约至少包括：

| 维度 | 最低要求 |
|---|---|
| 身份 | `experience_id`、`revision`、`supersedes_id`、`schema_version`、原始SHA |
| 来源 | 私有作品/原文版本SHA、单位/短句位置SHA、创建时的PASS A/B和角色事实账本快照 |
| 作用 | 具体适用情境/限制、预期改变的决策原语，而不是孤立术语与手法说明 |
| 认知 | 人物身份与知识边界、故事时序、观察/假说/替代解释/可反证条件、置信限制 |
| 证据 | 通过和失败的回执、独立语义评审状态、适用范围及本次使用后的结果 |
| 生命周期 | `CANDIDATE → REVIEWED → EXPERIMENT_ONLY`；或 `UNCERTAIN/REVOKED/QUARANTINED`；从未通过真实文学验收不可晋级 |
| 兼容 | 创建者工具/模型标识、协议和解析器版本、迁移来源SHA、目标SHA、兼容范围 |

不得原地改写旧候选、审核、负评、实验输入或R2 CAS；修正只能创建新版本并指向旧版，保留反例和撤销记录。稳定“知识”与低可信“候选”不可混用。

## 4. 乱码、遗忘、错用经验的硬性保护

1. **编码**：新结构化元数据使用严格UTF-8、规范化JSON字节序列和SHA-256；加载原著保持其原始编码及原字节SHA，严格可逆解码。无 `errors="ignore"/"replace"`，无静默重编码/原文NFKC覆盖。乱码、无效Unicode、混淆编码、双重解码歧义全部 `RESTORE_BLOCKED`。
2. **模式与迁移**：每种长期对象明示 `schema_version`；新版本读旧格式必须有明确迁移器及旧→新哈希链，保留旧原件；未知版本/字段语义歧义禁止“按最近格式猜测”或丢字段继续运行。
3. **写入事务**：先写不可变数据，再即时独立读回逐字节SHA，最后发布新的小manifest/指针。读者始终使用最后一个完整验证通过的快照；中途中断保留前一有效版本。SQLite用事务、WAL安全快照与完整性校验，不把内存缓存视为最终提交。
4. **冷启动恢复**：分别在至少两个全新进程恢复同一清单，完全验证对象SHA、事件链、引用完整性、schema版本和人物/时间关系；冷恢复失败时**不得**向WRITE输送经验，也不得自动重训/付费修复。
5. **能力退化**：每次升版用冻结盲题验证“旧经验是否仍可检索、是否仍按旧条件SELECT/SKIP、负例是否仍SKIP”。检测到行为倒退→暂停新经验晋升，隔离最近变动、保留原版回退点；不删除历史失败、不提升成功率以遮蔽问题。
6. **容量**：临时内存/缓存/索引有上限与淘汰策略，但**经批准的长期经验不得随便TTL过期**。长期存储量可以按作品与版本增长，应分区、分页、限每次加载量、做归档压缩与垃圾对象引用计数，容量用尽明确报错；禁止无限把整本书、整段模型回答塞进上下文。
7. **跨模型/跨版本**：不将“经验”仅放在某个模型的隐含上下文或供应商私有会话里。更换模型不允许改写保存的事实和审评结论，新的模型只能作为受限制的候选生成者；模型迁移要有固定对照测试，避免换模型后突然“退化/乱用旧知识”。
8. **双重确认**：哈希匹配证明没有变字节，不证明文学因果是真。即使经过V89原文定位，仍须V85可信人物知识、V86独立审核及真正新作品盲考，不让WF自己当唯一考官。

## 5. 发布门槛（不得以“存了多少章”冒充）

在允许“长期记忆可用”或解锁后续批量训练/正式WRITE之前，至少跑完以下**实际而不是文档里的**验收；失败要永久保留回执：

- **P0-01 持久落盘**：多个互相独立进程对真实已封存CAS做恢复、重算SHA与来源链，完全一致；验证上一个稳定指针仍存在。
- **P0-02 兼容迁移**：旧schema回放→新schema→再冷恢复，至少包括中文/特殊Unicode、旧字段、缺字段、损坏hash、乱码、非法编码与未来版本；不准无证据地“修复原文”。
- **P0-03 知识关系**：跨章人物身份、角色/读者知识隔离、反证/撤销、倒叙时刻与不完整事实，在恢复前后有相同的可核查结果；冲突必须显式 `UNKNOWN/UNCERTAIN`。
- **P0-04 行为选择**：同一冻结场景，升级/重启前后的经验版本、SELECT/SKIP与反例处理保持可追溯；若设计有意改变，需新修订+独立审核及差异报告。
- **P0-05 故障恢复**：模拟网络断开、CAS缺块、写manifest中断、SQLite事务回滚、磁盘写满、索引丢失、密钥暂不可用，保证前一已证实快照不会被覆盖、收费不被自动重复触发。
- **P0-06 长期负载**：分页回放大量作品/候选/负例，监控内存、时间、存储、重复与污染；不得通过只加载最初少量章节来伪装“长期恢复全部成功”。
- **P0-07 独立文学保真**：在未见新作品上做等条件有/无经验对照，检查错误率和实际文字质量；无独立可信语义裁决，就只能标记“工程持久化通过，文学成长未证实”。

发布门槛需在GitHub CI或独立Railway真实进程留测试/恢复SHA，并分别记录软件通过与文学未验证。**不以没有真实回执的漂亮演示代替验收**。
