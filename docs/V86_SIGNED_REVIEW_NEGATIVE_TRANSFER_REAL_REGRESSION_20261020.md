> **事实边界**：本轮确实改了GitHub源码，真实Railway全仓跑过两轮；所有“审核员签名”“小说段落”“模型假说”均为**合成测试夹具**，不是真人独立文学评审，不是DeepSeek新训练。本轮没有新的付费模型请求、没有真实R2访问或写入，没有修改前15章学习CAS，未发布到 main。正式文学等级仍遵循V49 `THIRD_STRIKE_FAILED`、第二学习窗口 `LOCKED`。

## 一、工作基线与目的

- 用户同意“真实原文 → WF产生可反证文学假说 → 独立核查 → 负例修订 → 下一次行为变化”，并强调底层可靠性。
- V85已实现封存PASS A来源锚点、FactJournal人物时间快照、仅候选不晋级；V61/V62已有受信实验批准、写前冻结、失败回馈与修订。实际断点是两套记录**没有受控、可恢复的语义审核衔接**。
- 从 `v85-literary-evidence-and-causal-memory-gate` 隔离出开发分支 `v86-evidence-review-negative-transfer-loop`，不修改旧历史/不运行GitHub Actions/不创造第二套关系数据库。

## 二、完成的源码修改

**1. `writerforge/v86_review_contract.py`**

定义来源审计绑定和独立审核协议：`audit_sha`、候选SHA、claim ID、锚点SHA、WF提议者ID，以及外部审核者ID、审核ID、结论和固定原因码。审核结论仅为 `SUPPORTED_FOR_EXPERIMENT` / `NEGATIVE` / `UNCERTAIN`。校验使用与V61受控实验授权不同的审核验证材料，签名无效、同人冒充两角色、合同哈希篡改都拒绝。多个追加意见里，**NEGATIVE 优先阻断**，UNCERTAIN次之。签名只能证明密钥持有者，不能证明真人、独立性或文学真值。

**2. `writerforge/db.py`**

在已有 `WriterForgeDB` SQLite追加 `experience_evidence_links` 和 `experience_literary_reviews` 两张有界小表，保持原有表与历史收据不变。只保存证据和审核的哈希、审核枚举、审核签名、关系ID；不存原著、训练稿或模型解释正文。独立审核按新review_id追加，已签旧结论不覆盖。

**3. `writerforge/experience_decision.py`**

- V86候选关联证据链接与candidate **同一SQLite事务提交**；缺证据／出错则不能留下半个生效的新V86链接。
- 新V86候选即使已有V61实验批准，**没有外部审查仍是UNCERTAIN，WRITE不获得该经验提示**。
- 已有合格签名的`SUPPORTED_FOR_EXPERIMENT` + 单独V61签名批准，仅允许有限的抽象操作进入WRITE。并不证明语义学会，也不能晋级。
- 追加`NEGATIVE`后，后续决策`SKIP/INDEPENDENT_NEGATIVE_REVIEW`。旧写前`SELECT`收据仍可读，但在正式再次使用之前必须重新核验，旧许可因负评失效。
- V86审查验证材料缺失／数据库哈希篡改时，拒绝写作选择而不默默退回可用状态。
- 没有新V86证据链接的V61/V62旧行为保留兼容，不重写旧候选。

**4. `writerforge/v85_pass_a_bridge.py` 与 `writerforge/v86_controlled_review_loop.py`**

- V86只能使用**同一会话里经过V85完整PASS A来源链验收**的收据。再次核对原文短引句SHA是否真实属于现有`source_spans`出处、原著版本SHA是否与`studied_works`一致、章次/快照是否对应。
- 原著句子只在验证时存在于私有进程，持久结果仅有哈希和位置；没有把原文剧情送给写作提示，也不从别的作品复制角色同名关系。
- 修订必须满足V62“前版有负证据且操作/条件改变”，**还额外要求新的V85已封存假说ID和新的审计SHA**，防止仅换经验编号便洗掉旧失败。即便新修订提交成功，仍需全新独立审核与实验批准。
- 仍不让AI自己生成外部审核签名。本轮只使用合成测试私有注入密钥；没有要求用户重配Railway原三种凭证，且没有真正部署生产外部审核机构。

## 四、审查剩余P0，不可声称已解决

1. **V86仍是隔离代码的合成闭环，不是“真实文学能力闭环”**。真实WF模型尚未在新协议中生成带原文位置、反例和可证伪条件的候选；未由可信独立文学考官逐条确认语义。
2. **独立身份**：合成HMAC签名只能证明验证器匹配，不能独立证明审核者是真人、与WF组织独立、或审核意见正确。生产需要真实受信签发流程。不能让WF模型持有审核签名权。新的审核材料没有在用户Railway上配置，本轮**不新增第四个配置步骤**。
3. **FactJournal的KNOWN为“已记录知识断言”**，不等于原著真实含义；当用户实际希望校验“人物当时知道什么”时，还要独立建立有来源的事实录入流程，不能让同一模型先写事实再拿它自证。
4. **只有V86明确通过的入口**才有这条新控制面。V61老调用者、可信宿主直接SQLite写入/底层写作入口等仍按既有信任模型运作；无法凭新表证明所有第三方宿主绝对不能绕过。
5. V86新增表存本地SQLite、原V79–V82事件还在原Cloudflare R2 CAS池；真实跨账本事务、云端迁移/恢复、冷启动独立鉴权尚未进行。不能叫作原生LEARN Worker生产成功。
6. 评分与文学实验未进行：没有新的盲题、写作原创、等长对照、真人独立认可；V49 `THIRD_STRIKE_FAILED`及第二窗口`LOCKED`仍不变。第16章V83因错误SHA预付费失败，不应重跑1–15章。
7. 目前Railway最近一次配置为`python -u wf_railway_v85_full_offline_regressions.py`、`restartPolicyType=NEVER`，即一次性无外网离线合成测试；不自动付费。测试后状态须以读回Railway最新配置为准，不能声称已切回`safe_idle`，除非有明确部署与实际日志。
