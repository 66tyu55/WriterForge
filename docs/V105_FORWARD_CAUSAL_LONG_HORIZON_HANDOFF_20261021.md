## A. 先回答长远问题，而不只给当前错误贴补丁

旧流程关注眼前场景出现了什么动作与后果，V102开始记录未解决情感和损失。V104十篇真实文稿揭示这仍不足：很容易先让人物做出一个看起来热血的决定，然后在数百字后才发现动力已断、选项只有一次、角色不在该地点、钱从未付过或关键资源突然出现。

V105增加两个互不混淆的边界：

1. **写前候选前瞻**：只在手动选择F模式时，复用现有章计划那**一次模型调用**，让WF同时提出2—3条互斥候选未来；各1—4个有前提的行动，包含需要的资源/位置/已知信息、可能改变的状态、潜在损失、下一次不处理损失的后果。宿主不替WF选“最优秀路线”，只机械查验已被调用方明确声明的初始条件、计划内部互相冲突的前提，以及某个前一动作能否在符号层面支持或破坏下一动作。缺数据=>UNKNOWN，不是真伪判决；可写安静、倒叙和开放结尾。
2. **写后候选债务**：原V96/V102实际正文短引句校验先通过，再把人物自称情感、损失和未解决压力存为带SHA的候选债务。下一章**必须仍看到未解压力**；原模型口头说“我会赔”或“一切过去了”不能自动清零，也不能凭此宣布赔偿已经兑现。不可逆损失被补偿不等于从没发生。

借鉴已有方法而不是安装大型第三方技能：AIMA的[Partial Order Planner](https://github.com/aimacode/aima-python/blob/master/notebooks/planning_partial_order_planner.py)的开放前提和因果连接/威胁；微软[Event Sourcing](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)的追加式事件和可重建投影；[Saga](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)强调补偿不意味着历史没发生。没有把这三个项目的实现复制入WF，也没有新模型权重或新的存储数据库。

## B. 已修改的真实WF代码

- 新纯函数内核：[writerforge/v105_forward_horizon.py](../writerforge/v105_forward_horizon.py)：
  - 2—3条替代未来，各最多4步；作者/调用方明示初始事实最多48条。任一计划事实有唯一键（如power:station / actor:hero / permit:letter），模型不能把自写前提变成权威世界事实。
  - 结构化requires、sets；已确认初始条件相反=>CONTRADICTS_PINNED_FACT；先关闭电源却后要求电源开启=>THREATENS_PREVIOUS_PLANNED_EFFECT；未知电池=>UNPROVEN_PRECONDITION；先取钥匙后用钥匙=>SYMBOLIC_CAUSAL_SUPPORT_UNVERIFIED。**软件只声称符号约束，不声称人物文学因果被验证。**
  - 代价forecast分为潜在、重大、不可逆；未来期限内无处理、未来承诺赔付、企图用补偿“撤销”不可逆损失都要留风险标记。预测的未来代价未发生，不得当做已支付。
  - 从V102原文签收恢复实际候选压力，跨章复制所有未解债务到下一条带SHA的回执，并存parent SHA，允许显式从老任务回执接续；checkpoint最多48未偿项、48KB内，超过**拒绝继续自动生成，而不是静默丢掉旧债**。此限制是V105原型的容量保护，不是无限长篇支持。
  - 有限上下文只投影最相关的末尾压力；少显示了几条就必须显式写“还有N条仍在完整账本中”，不能当已解决。每份初始事实的真实性需可靠的作者/FactJournal审签，调用方自报不能构成独立法律/科学/文学核实。
- [writerforge/writing_assist.py](../writerforge/writing_assist.py)：加入 opt-in F=foresight_rolling。章计划输出预约上限从旧模式650提升到F的2400 tokens（**规划调用数相同，token成本可能增加**），一旦整个候选未来都明确违背作者已声明状态，停止后续生成并记红案，不自动重试。随后仍使用V98同次数滚动重规划、V102情感原句合同，F额外保存v105_prospective_horizon.json、v105_unreviewed_open_debts.json和哈希回执。跨同一任务两章自动传候选压力，也允许以后显式输入上一任务候选回执；不把它晋升为正式世界事实。
- [writerforge/studio_server.py](../writerforge/studio_server.py) 与 [writerforge/ui/studio.html](../writerforge/ui/studio.html)：在旧A/B/C/D/E之外可手动选择F，默认仍是A、不自动训练。网页未提供可信事实输入，故不应把任何没有证据的事实标为已确认；明确说明无作者已核实世界条件时只能检测内部预测矛盾、其余标UNKNOWN。

## E. 不能只看现在：长期演进必须提前规划的边界

1. **来源层**：要让硬约束成为可信事实，须从已有FactJournal或作者真正接受的设定加载，尊重时间戳/角色视角/来源证据；不可让WF写一句“我知道”就覆盖真实记录。角色撒谎、怀疑、幻想必须可以存在。
2. **生成层**：章计划前瞻只列关键条件和后续债务，不能强制每章三次反转、牺牲或大场面。安静场景、不发生硬状态改变同样是文学。写作E/F要长期对比真实文本自然度，防止预演生成说明书风。
3. **状态层**：目前F只把未接受候选回执保存在原作业目录，**还不是正式跨机器永久R2可信事实链**；接续需要显式传入签收回执。下一轮若要规模化，应把审查后可晋级的正文事件交给原StoryCommit/FactJournal，再采用原R2不可变存储/恢复；不新建平行百科图谱。不够空间时必须有有审签的已清算债务归档，而不能丢旧数据，避免内存无限增长。
4. **核验层**：事实条件不矛盾不等于剧情精彩，更不代表人物做法自然。需要用旧V104相同十题、不改历史原稿做E/F相等正文长度+同模型调用预算测试，记录真实模型成本、首个因果失效位置、未解代价密度、独立读者的多维评价。不能用F程序PASS证明F文学胜利。
5. **运行层**：生产Railway wf-python-r2仍原安全 idle，没部署此隔离分支、没有新增真实模型请求，不碰15章历史。只有明确批准新实验时才考虑受控部署，强制调用次数/实际字数/超时无重试。
