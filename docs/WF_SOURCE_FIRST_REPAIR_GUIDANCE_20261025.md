# WriterForge 0.T｜从「发现了问题」转成「真正帮助写作 AI 修复，并避免越修越乱」（2026-10-25）

> **纠正前一阶段的主线**：不能把 WriterForge 当成“给 AI 发出问题提醒的程序”。真正的写作闭环必须是**已有作品和真实前因 → 原作者自己选择修改目标 → WF 提供来源锁定的可执行修复约束 → 同一模型写出修改／仅重引因果证据 → WF 比较修改前后风险并保留有效来源 → 必要时回滚／重新创作受影响的下游**。任何一步没有通过，就不能说小说已经变好，也不能把未验收废稿写成 Canon。

**实际改动**：仅 `refactor-unified-scene-delivery-audit`，在原 `writerforge/v119_revision_transaction.py` 与 `writerforge/writing_assist.py` 内增强，没有新文学记忆主人、外部审稿模型、自动训练、默认增费功能。完全不动 `main`、Railway、用户 R2 原著、任何已接受作者正文。V26、V98、V96/V114/V117、统一 NarrativeCore、现有 Studio 与取消/保留废稿继续有效。

## 一、问题的本质：失败码不是修改指导

前次 [真实 DeepSeek 戏楼单句 V119 #40155863914](https://github.com/66tyu55/WriterForge/actions/runs/40155863914) 中，**创作 AI 已自行选择 `LOOK_BACK_NOW`，并亲自写出更有谨慎预判的动作修订**，但它把整个 replacement 同时填写到 `trace.action_quote` 和 `trace.effect_quote`，V96 正确报 `WF96_ACTION_EFFECT_OVERLAP_OR_REVERSED`。

过去的流程是：报错 → 保留原文 → AI 下一次又可能从头改写 → 产生新物件/时地/人物知识错误 → 再报错。这虽保护了旧稿，却没有充分帮助模型克服**到底是小说写错，还是引用元数据错**的差异。用户明确指出，这样最终还是「改来改去的错误」。

## 二、第一层：修改前的来源锁定「修复契约」

原 V119 新增 `prepare_source_repair_contract`。每次真正调用作者模型之前，实际保留并向**同一模型**提供一份有 SHA 的有限合同：

- **原文是什么**：原稿 SHA、模型自己真正选中的唯一原句及字符偏移，**不由宿主创造修改目标**。
- **为什么修改**：原写作 AI 的 `reason / risk / desired_effect` 原样标为“模型意图，尚未被真实作品证实”，不是 WF 生成的剧情。
- **之前真正有什么**：V96 被接受的前一段真实 `effect_quote` 或没有父事件时为 null；V114 原本已有的**仅候选**物件所在处、角色受伤状态等来源字段，有限最多8项，并明确任何遗漏、其他域未展示并不代表状态消失。
- **有哪些风险不能隐瞒**：原 V116 在**修改前**已经发现的硬冲突及未确认项，这些不会因为生成一份新稿就被一笔勾销。
- **可供原作者选择的修复路径**：保留有意留白、针对源原句局部改、删掉不能成立的过渡，或本人决定整场重写；每个路径都要保留已有真正前因、不能替人物凭空新增秘密/物件转移。**路径是可选操作，不是 WF 给出的新小说句子**。
- **下游影响**：如果这一事件段真正变化，原来依靠它写出的后续文本必须标记为派生失效并由原作家重新生成；不能直接把旧第二段拼到新第一段上称为新完整章。

每轮的完整合同原字节保存于同一私有 job 的 `round-XX-source-repair-guide.json`，模型收到对应源证据；若硬约束全文超过模型 prompt 预算，**跳过请求**而不是暗自丢失状态事实。

## 三、第二层：不是检查单一错误，而是比较修复前后的实际风险变化

原 V119 新增 `compare_source_repair_impact`，直接复用旧 `preview_revision` 和 V116/V122 的真正前后来源风险报告：

| 比较项 | WF 允许得出的结论 | 严格不允许得出的结论 |
|---|---|---|
| 改动范围 | 原文选区、未改动前缀后缀、source SHA 真实吻合 | 这段更好看 |
| 旧冲突消失 | 某些旧**机器可核**的风险没有出现在新稿报告中 | 小说的动机/情节已经完全修好 |
| 新增硬冲突 | 阻断候选，并保留旧稿 | 让程序代替模型改写 |
| 新增但语义未证明的疑问 | 新候选**私有待核**，不能自动推进后文；当前源仍有效 | 把不确定的正则/读者猜测直接判成事实 |
| 原来就未解决的冲突 | 新回执明确列出“仍在”，不能把结果标为全清 | 借局部文字变化清空原先因果债务 |

结果保存在 `round-XX-before-after-impact.json`，有独立 SHA，可核对旧风险、已消失风险、新增风险和**仍未证实**的审阅项。它没有额外模型调用、没有永久经验晋级或任何 Canon/R2 写操作。

## 四、第三层：不会让 AI 在 A→B→A 无限打转

V119 同一个用户任务在内存里跟踪**真正已通过来源校验**的候选原文字节 SHA。若第二轮想改回以前出现过的版本，记为 `REJECTED_REVISION_OSCILLATION`，保留上次有效版本、保留该模型原始失败方案和耗用次数，不再继续循环。

旧错误导致这次候选无效时，私有输出 `round-XX-actionable-failure.json` 明确区分因果来源引句不合法、缺失父事件、源空间警告等，给出**该由原作者补什么来源证据**的下步动作，而不是只输出一个晦涩的错误码。这些目标不替 AI 判断文学好坏。

## 五、第四层：小说文字已经写好时，优先修「引句元数据」，不让小说反复重写

这是本轮最具体的协作改变：

当且仅当**真实模型已经生成一份可源锁定位的 V119 新正文**，失败原因严格限定为 V96 可修的引用层错误（例如动作与后果引用重叠），而且作者本次任务明确允许 **`self_edit_rounds=2` 且仍有模型调用额度**时，WF 可自动在**同一用户任务内**请求**同一个创作模型**：

> **原文冻结不许改一字。这次只需要在你自己已经写出的候选里面重新选择 action_quote、effect_quote 和 parent_effect_quote，不能返回 prose、replacement 或新的剧情。若找不到合法动作/结果引用，就如实失败。**

- 第二次回复必须严格为 `{"trace": ...}`（仅兼容旧 API 已真实出现的独立 `type=json_object` 包装）。程序**不自动生成或切割三个引句**，作者模型自己重新阅读并返回；V96 仍对实际正文精确核验先后/唯一性/前因。
- 如果这次只改引用成功，小说正文仍保持**第一次模型亲自写出的完整新段**，随后继续按原 V114/V117/NarrativeCore 核对。回执明确记录**额外使用了同作者模型1次引用补交**，不会第三次重写。
- 如果第二次仍错、格式不合法、用户取消、或预算不足，严格留旧稿、保存两个原始回复及明确失败原因；**不能假冒“来源已修好”**。用户取消行为依旧是用户取消，不得被吞掉或视为普通文学否决。
- **默认没有新调用**：没有开启第二轮自主审改的旧路径、原 A–F 和普通稿件不触发补交。两次请求均计入既有单作业模型预算，不新增外部模型、不提供假免费额度。

**这次架构转向的核心**：WF 要成为会查前因、能指导修改范围、监视连锁后果、阻止错误振荡的可靠小说创作协作系统；但“人物为什么这样做、怎样写才有美感、是否值得推翻”，仍然只能由创作 AI 和实际读者评价。
