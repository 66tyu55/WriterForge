# WriterForge｜作家式自我删改的核心创作流程（2026-10-24）

本轮仅修改开发分支 refactor-unified-scene-delivery-audit；不改 main、Railway、用户私人小说、已封存 Atria 实验和既有 Canon。用户核心要求：作者只提出一次创作需求，让 WF 像作家一样，写着写着自己不满意便删句、改段、推翻某场、再继续，而不是作者连续重发“再写一遍”，也不是外部模型替 WF 写。

## 一、原始核心必须保留

- 早期 V26 本地 Studio：两种不同原创续写、作者采用或忽略、Ctrl+1/Ctrl+2、手稿自动保存、内部素材和技法调度；真实候选绝不自动接纳为著作。
- V27 逐级文学训练；V98 已写正文驱动滚动重规划；V119 只修改选定原句、原段的事务预览与状态检查。后续 V114 物件时态、V117 原章恢复、V96 动作与实际后果、现有统一 FACT/UNKNOWN 和未偿 THREAD 都继续工作。禁止建立另一套平行的事实、经验或角色记忆数据库。
- Studio 原有 A–G 创作选择、人工逐段继续、作者中途停止与丢弃本次未完成候选保留；**作者要求删除整个任务**和**WF 自己在内部决定删改一句**不是同一种行为。

## 二、新闭环：一个作者请求，WF 在内部多轮创作

原创构思 → 真正写出当前段原稿 → 同一写作模型自己重读 → 自己选择 KEEP（保留）、DELETE（删句）、REVISE（改句或段）、REPLACE_SCENE（整场作废重写） → 旧 V119 原文位置与 SHA 验证 → 旧 V96 动作、后果及前因验证 → 统一事实/时态检查 → 形成新的未接受候选 → 下一段继续依据**修改后真正出现的文字**往前写。

不为提高“删改次数”强迫 WF 重写：如果已经自然，可以主动选择 KEEP。删掉不满意的文字前，已经发生的情节仍是约束；失败改动不能让人物凭空知道秘密、恢复伤口、转移物品或抵消时间/代价。模型自我审稿属于来源有限的创作建议，**不是独立文学质量裁决**。

## 三、当前已实现的工程边界

- 在现有 writerforge/writing_assist.py 中加入一段自主候选编辑循环，只有显式选择 G 统一叙事模式才能开启；其他 A–F 保留原逻辑。self_edit_rounds 默认为 0，可选每段 1 或 2 轮；整个作业最多 8 次额外相同模型调用，每次模型回复上限 1800 tokens；失败不无限重试，不能依赖用户再次发送。
- 一次删改片段最长 1800 Unicode 字符，通常足以覆盖当前 G 事件段；其他事件段、前章原稿不可被模型擅改。每次 V119 使用 SHA 保护原文，修改后必须重新完成 V96 及现有 V117/统一来源的严谨检查；否则回滚到该轮的原稿。只能确认为**候选版本可继续写**，不能据此晋级永久文学经验。
- 之前模型提供过完整原句但算错下标。现在若原句在当前稿中逐字**唯一出现**，宿主可零额外模型调用定位准确起止，仍让 V119 验证；如果同文出现多处、源 SHA 不符或改动范围不合法，必须拒绝，禁止模糊匹配。
- 废稿与每轮自审原始模型提案会写入当前 job 自己的私有工作文件夹，包括首次原稿、已舍弃文字、选中版本和 SHA 收据；本次作业到期/作者主动丢弃时随该作业清理，不把废稿丢进独立长期记忆。其他任务与作者手写原稿保持独立。
- 本地 Studio 在原 G 模式提供自主删改 0/1/2 轮选择。选用自主模式默认关闭“每段都等用户点继续”，真正能由 WF 在同一个请求里自行推进；作者仍可主动暂停/停止/丢弃。该开关尚未默认强制所有用户启用，必须先拿真实文学 A/B 证明不会负迁移。

## 五、仍未实现：作家判断力不是自我改稿按钮

这次证明了自动提出删改、精确改稿、回滚和继续写作的工程闭环，不证明 WF 已具有优秀小说家的鉴赏力。还须让 WF 在多个全新故事中自行识别不合理人物知识、过度重复、代价断裂、伪情绪、过早解释谜底；再看实际作者/读者是否喜欢改后版本。独立文学审评不可拿同一模型对自己的“满意”评分替代。

未来可以从“整场被推翻”的版本继续重新规划下一幕，但绝不能把旧废稿里的事件留作已发生事实。要做同源第一段固定的真实长文对照，比较不开、开一轮、开两轮的变化与失误，并记录在哪一行开始出错。试写次数不是目标，**敢于保留好稿、敢于作废坏稿、不会把坏改动写入真实故事**才是目标。
