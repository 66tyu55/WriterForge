# WriterForge 统一叙事核心：延迟压缩、源文回查与人物自主性

日期：2026-10-22。当前分支：refactor-unified-narrative-core。
定位：对既有统一叙事核心进行合并改造，不新增一套平行记忆数据库。

## 用户最重要的原则

“作家不是预设读者希望看到的剧情。人物应有各自经历、认识、性格、欲望与顾虑，和其他人物及条件发生碰撞后，情节可能沿计划外的方向自然发展。”

因此 WF 的思考/写作流程应遵循：作者构思可提出方向，但不宣布结局；模型生成的情节只有实际写在文字里才成为候选事件；状态/知识/目的的变化必须以原文证据和复核为准；不要强制所有人物按大纲或读者偏好走。

## 现存事实性底层与叙事底层不能混淆

- Novel Studio 固定 MIT 时态归约器（V114/V116/V117/V122）：物品、部分人物伤势、明确来源动作的候选时间状态。严格源文检查，仍不是通用自然语言理解。
- 统一 Narrative Core：人物知识 KNOWS / BELIEVES / UNKNOWN、CONTACT、通用 THREAD、来源证据、稳定 ID、优先级调度。接入 continuity_guard；旧 V123 复仇专用状态仅兼容，不能和新图共同拥有长期目标。
- 当前已在统一核心中加入 CHARACTER_REFLECT 人物倾向事件，限作者确认、有唯一原文片段。人物 desire/fear/value/temperament/habit/emotion 等不自动代替决定；在本章构思时可分别呈现不同人物的顾虑，允许改变计划。

## 章节记忆的三级规则

1. **绝不可被摘要覆盖**（事实语义层）：原始小说文本、原文哈希、明确发生的事件与时间位置、物件和任务道具的归属、人物知识边界、人物与人物的已确认关系、尚未兑现的承诺/伏笔/冲突、作者明确设定以及任何原文可决定后续因果的条件。保护层依然受限于 WF 当前结构化事件检测范围：不能声称所有隐含事实都已自动提取。
2. **允许有损凝练**（文学过程层）：场景气氛、温度/光线/声响、节奏、语言风格、动作微细节、人物情绪波动、独白、印象、尚未证实的推测。若某细节承担伏笔、象征、关键因果或人物重大转折，必须额外保留来源/结构化锚点，不能贸然只保留一句摘要。
3. **延后压缩的工作缓冲**：保存完整原文候选以后，才保留最近 3 章较丰富的源文片段；满 3 章后，最旧的一章才转换为可追溯的温记忆；最多保留 8 章温记忆，之后按内容哈希写入已有本地候选目录下的追加式冷档。未成功写入时必须拒绝归档，不能悄悄丢失。

具体入口：writerforge/narrative_core.py 中 record_chapter_memory、recall_original、relevant_history_context、buffered_memory_context、character_collision_context；写作端 writerforge/writing_assist.py 中单一写作前调度入口与候选章节保存接口。

热记忆不是整章永久复制：长章节只在工作内存保留带清晰不完整标记的片头与片尾，其余部分始终保留于候选原文档，必须用 SHA 校验才能回查。当前自动摘要的兜底是有限原文摘录。模型概括只可放入明确标记 MODEL_PROPOSAL_UNVERIFIED 的候选温记忆，必须附 1–6 条原文精准引句，经真实原文校验；不能根据“摘要自称已经发生”更改任何人物或事件状态。

## 新增关键闭环：老章节不是只压缩不使用

relevant_history_context() 在章计划确实提及关联 FACT / THREAD 节点时，沿温记忆与内容哈希验证的冷页检索相关原章。只有原始章节源文件的 SHA 校验通过，才截取少量实际原句给作者级构思提示。模型写的摘要不进入此原文证据窗口。只提主角名字而没有具体秘密/双人线索时，不能因此把全部旧章唤醒。阅读者视角与具体 NPC 个人认知仍是分离的，出现秘密原文不能变成角色知道秘密。

此实现的冷索引目前是有界页链回查，最多 1000 页；对几百章能测试，但大规模跨卷频繁查询仍需要云端 R2 的索引和冷热分级。**目前真实运行只实现本地追加式冷归档，不要声称已把新记忆发到 R2。**本地模型生成路径仍有限制，不能因为已经有 Discovery 免费额度就假设生成/压缩全链已经端到端成功。

## Discovery/DeepSeek 实测，不可以谎报

一次人工合成测试原文的有限试验：https://github.com/66tyu55/WriterForge/actions/runs/39787584722
共尝试 2 次调用：
- intern-s2：TimeoutError
- deepseek-v4-flash-0731：HTTP 429
没有生成可审核的压缩摘要。原工作流 SUCCESS 只代表安全执行与报告生成，**不代表供应商推理成功，更不是小说文学质量提升**。已更改该脚本的结果状态，失败时返回非零，并将试验工作流改为手动 workflow_dispatch、上传失败凭据 always，以防 push 自动再次消耗赠送额度。上述改动未重试模型。

已存在 Discovery GitHub Secret 与官方 OpenAI 兼容型 provider 入口，但本轮不得推断用户的具体墨点余额、模型限额、今日 429 的准确原因；也不能把两次请求误称为两次成功。

## 当前完成程度与下一步真正缺口

完成：统一叙事核心内的候选写作缓冲与延迟压缩、保护性结构化事实、按需从温/冷恢复旧章节原文、人物自主欲望与价值观的规划提示、原稿不删除与出处核验、实际写作路径的上下文预算协调；没有继续叠加散乱单用途模块。

未完成：
- Discovery/DeepSeek 仍未验证真正可用的压缩语义质量；收到 429/超时后不自动循环重试。
- 人物性格、心理、气氛、因果锚点尚不能从任意中文段落自动可靠抽取；当前字符 lens 变化需要源引句和作者确认。避免把模型猜测冒充事实。
- 当前冷档是本地追加式 JSON CAS，并非 R2 云端持久化；需要把已有 R2 客户端接入同一个原文/压缩索引，而不是另外建“独立作家记忆库”。
- 真实软件部署、20/100/300 章的自发创作水平、因果连贯性和文学盲评尚未由此证明；仍需要独立同模型写作评估。

所有本轮改动只在 refactor-unified-narrative-core 分支；生产 main 与 Railway 未改。本轮新的 R2 写入 0，正典写入 0；唯一真实模型调用尝试为单独合成样本探测的 2 次。
